# Mouse Laboratory Management System — Prototype

Interactive clickable prototype (mockup) for managing lab mice. **UX-first: built to test the workflow with real lab users before any real backend is written.** Everything runs in the browser with in-memory mock data — no database, no build step, no framework.

UI language is **Thai**. Keep it Thai unless told otherwise.

## Run / verify
- Open `index.html` directly in a browser (or the Launch preview panel). No server needed.
- After editing JS, sanity-check syntax: `node --check js/data.js && node --check js/app.js`
- Data resets on every page refresh (in-memory only) — this is expected.

## Files
- `index.html` — shell; loads the embedded font, CSS, then `data.js`, then `app.js` (all cache-busted with `?v=N`).
- `css/styles.css` — all styles. Uses CSS variables in `:root` (colors, radius, shadow). No preprocessor.
- `js/data.js` — mock data + `Data` helper object. Project 1 (NAFLD) is generated by a loop: 4 shelves × 6 cages × 2 mice.
- `js/app.js` — the whole SPA: `App` controller object (routing, rendering, all dialogs, weighing wizard).

## Architecture
- **`App`** (js/app.js): single global object. `App.init()` runs on DOMContentLoaded. Views are rendered by string templates injected into `#root`. Navigation via `App.go(name, projectId)`; `App.shell(crumbs, body)` wraps the header. Views: `renderLogin`, `renderProjects`, `renderDashboard`, `renderReports`, `renderCreateProject`, `renderBuildProject`, plus modal builders (`openCagePopup`, `openMouseDetail`, `openTreatForm`, `openDeathForm`, `openHumaneForm`, `openIntakeCage`) and the weighing wizard (`startWizard` → `renderWizardStep` → `renderWizardReview` → `wizardSave`). The dashboard has three mutually exclusive modes: `App.weighing` (ชั่งรอบปกติ), `App.intake` (รับหนูเข้ากรง), `App.editing` (จัดการกรง, with `App.editMode` = diet|group|move).
- **`DB`** (js/data.js): `{ users, currentUserId, projects[], auditLog[] }`. Each project: `{ id, name, approval, status, shelves, cagesPerShelf, shelfNames, facility, diets[], groups[], cages[], members[], documents[] }`.
- **`Data`** (js/data.js): derived helpers — `getProject/getCage/getGroup`, `controlGroup`, `inStats(m)`, `latestWeight/prevWeight/weightChange`, `cageAvgWeight/cageAvgChange`, `controlAvgChange`.

## Data model (per mouse)
```
{ id, code, sex('M'|'F'), groupNo, cageNo,
  // code = IDENTITY, permanent: `<projectId>-<cageCode>-<cageNo>` (e.g. P1-A-01-3), built by
  //   `mouseCode()` in data.js and issued by Sci at the FIRST WEIGHING (intake).
  // cageNo  = ลำดับในกรง — a 1…5 sub-number, unique inside its cage (part of the code).
  // groupNo = ลำดับในกลุ่มสารทดสอบ — null until the PI assigns the cage a group; part of the TAG, not the code.
  weights[{date,weight}], remark,
  treatments[],    // Sick Case Report entries: { date, time, vet, signs[], support[], diagnosis, treatment, recommend, note }
  excluded,        // "stopped": kept out of group-average stats, still alive & eats/drinks
  alive,           // false once Death is recorded
  death,           // { type:'natural'|'humane', disposition:'dispose'|'necropsy', note, date }
  careOpen,        // vet case currently open → drives the cage "care" (yellow) colour
  humaneOrder,     // vet order to euthanise: { reason, vet, date }
  necropsy }       // Necropsy Record (only when death.disposition==='necropsy'):
                   //   { date, time, examiner, results:{ [organ]:{v:'N'|'A'|'X', note} }, abnormal, avComment }
```
Cage: `{ id, code, shelfLabel, dietId, groupId, shelf, position, mice[], water/food:{…}, status(legacy), lastRecordDate }`.
Project: `{ …, diets[], groups[], cages[], facility:{roomNo,rackNo,quarantineDate,moveInDate}, shelfNames{} }`.

**Two-layer experiment grouping.** The design is 2-factor and each layer is assigned **separately, after the mice are already in their cages**:
- **Layer 1 `p.diets[]`** — ชนิดอาหาร `{ id, name, isDefault, color, desc, capacity }`. `cage.dietId === null` ⇒ the cage falls back to the **default diet** (อาหารทั่วไป). Exactly one diet carries `isDefault`.
- **Layer 2 `p.groups[]`** — สารทดสอบ `{ id, name, isControl, color, desc, capacity }`. `cage.groupId === null` ⇒ not in any treatment group yet.
`capacity` on **both** layers = max mice the PI may put in it. Read them only through `App.cageDiet(p,cage)` (never `cage.dietId` directly — it hides the default fallback), `App.cageGroup(p,cage)`, `App.diets(p)`, `App.defaultDiet(p)`, `App.dietCountLive(p,id)`, `App.popGroupCountLive(p,id)`.

**Mouse identity + TAG.** The permanent `code` carries no grouping — mice enter the project before any group exists. Once the PI has grouped the cage, a **display tag** `อาหาร-กลุ่ม-ลำดับในกลุ่ม` is appended:
```
P8-A-01-1                              ← ยังไม่จัดกลุ่ม
P8-A-01-1 (ไขมันสูง-Treatment-1)        ← grouped
```
The tag is **derived, never stored**: `App.mouseTag(p,cage,mouse)` → `''` when ungrouped, `App.mouseLabel()` = code + tag (used in PDFs/CSV), `App.tagChip()` = coloured chip for on-screen lists. Only `groupNo` is persisted.

**Identity vs. location (move-cage-ready).** Physical location — room / rack / shelf / cage — is *current status*, derived from whichever `cage` holds the mouse (cage → `shelf`/`position`/`shelfLabel`, project → `facility.roomNo`/`rackNo`); it is **not** duplicated onto the mouse. Compose it only via `App.facilityLine(p)` / `App.cageLocation(p,cage[,withCage])`. All personal data (`sex`, `weights`, `treatments`, `death`, `necropsy`, flags…) lives on the mouse, so moving a cage between shelves (or, later, a mouse between cages) needs no display changes. The cage card's per-row number uses **`m.cageNo`**, never a `code` substring — group names contain `-`. New project ids come from `App.nextProjectId()` → short `P<n>` so the code prefix stays compact.

## Key domain rules (keep consistent)
- **Auth model — two tiers, purely additive** (see the block comment at the top of `js/data.js`):
  1. **POSITION** (`POSITIONS`, `POSITION_ORDER`) — **exactly one per account**, in `DB.users[].position`: `ADMIN, AV, VET, SCI, ACT, AEC, IACUC, QA, AUDIT, EX, OCH, GM, EXTERNAL`. Each has `caps[]` and a `scope`: **`'all'`** = sees every project without being appointed, **`'member'`** = only appointed projects (`EXTERNAL` only). Nobody holds two system positions; a person's "second role" only ever comes from a **project role** (an internal Sci who runs a study becomes PI of it; an outsider is only ever EXTERNAL — a real-life vet with no system VET position gets no vet powers). `App.positionKeys()` returns the one position as a **one-element array** so `.map/.join/.includes` call sites stay uniform.
  2. **PROJECT ROLE** (`ROLES`, `ROLE_ORDER`) — per project, in `project.members[] = { userId, roles[] }`. `PI`/`COPI` are identical to each other; `AHS` does the dosing. `SCI`/`VET`/`ACT` mirror the caps of the system position of the same name **but only inside that project** — that is how an EXTERNAL vet works on project A without seeing project B. For someone who already holds the position it adds nothing, so it reads as a paper appointment; there is **no `nominal` flag** any more.
  **Effective capability = every position's caps ∪ every project role's caps. Nothing is ever subtracted.** Gate through `App.can(cap, project)` / `App.hasAccess(project)` / `App.canEnter(project)` — never test a key directly.
  Key splits: `stop` = **PI/CoPI only**; `treat` = AV/VET; `weigh` = **SCI only** (a PI who wants to weigh must also be appointed Sci of the project); `dosing` = AHS; `cageCare` = ACT; `viewReports` (the graph page) is denied to IACUC/QA/AUDIT/EX/ACT/OCH/GM — it is the researcher's result, not welfare data; `approve` + `manageMembers` + `manageUsers` = **AV** (+ADMIN) — PI lists the requested appointments when submitting and AV maintains them afterwards.
  Helpers: `App.positions` / `positionKeys()` / `positionLabel()` / `hasPositionCap()`, `seesAllProjects`, `myProjectRoles(project)`, `isCreator`, `isApproved`.
- **Death is a two-stage flow**: `reportDeath` (anyone on the team) sets `death.carcass='frozen'` with `disposition:null` — the carcass goes to the freezer; then `handleCarcass` (**SCI/VET only**) sets `carcass:'done'` + `disposition:'dispose'|'necropsy'`, and necropsy opens the 11.3-01 form. `App.deathLabel` renders the frozen state, and `openCagePopup`/`openMouseDetail` show a **จัดการซาก** button only while frozen. The old single `deathStop` capability no longer exists.
- **OCH is view-but-never-enter**: it holds `view` + `ochReport` and **no `enterProject`**, so `App.openProject` routes its card clicks to the safety-report page instead of the dashboard, and `renderDashboard` bounces it.
- **Project roles are dormant until approval**: `myProjectRoles` returns `[]` for a waiting/rejected project unless the user is `project.createdBy` (who acts as PI to fix and resubmit). Every project therefore needs a **`createdBy`** field. AV still sees such projects through its position scope, for review only.
  **Demo switcher**: floating panel bottom-right (`.demo-fab`), grouped into *ตำแหน่งระดับระบบ* (one persona per position) and *บทบาทในโครงการ* (u_pi/u_copi/u_ahs). The latter carry `user.projectRole`, which makes `myProjectRoles` return that role in **every** project so a client can compare views. Real deployment: nobody has `projectRole`; membership drives it.
- **Project creation is a THREE-stage pipeline that ENDS at AV** (`approval`): PI submits a **request** → `requested` → **AEC** (สำนักเลขาฯ จริยธรรม, position with `reviewAEC`) approves → `aec_ok` → **AV** (`approve`) lays out the facility + **empty** cages and confirms both group layers → `approved` = **LIVE**. Either reviewer can set `rejected` (with `rejectStage:'aec'|'av'`); only the creator resubmits (→ back to `requested`). A pre-`approved` project has **no cages** — it carries a `request` blob (`totalMice`, **`diets[]`** and `groups[]` each with `plannedMice`, `diagram`/`aup`/`approvalDoc` attachments, requested `appointments[]` of CoPI/AHS). `App.approvalStage(p)` + `App.stageInfo(p)` centralise the state; `App.isReal(p)` = `approved`; `App.isEmptyProject(p)` = live but no mice yet; `App.canReviewAEC`/`canBuild` gate the two review actions.
  - **AV build** (`renderBuildProject`, stage 3): room no. **(string)** + rack no. **(string)** + quarantine/move-in dates; **both group layers** are confirmed here — PI proposes them in the request, AV edits/approves (`renderBuildDiets`/`captureBuildDiets`/`updateDietSum` mirror the group trio; the radio marks the **default diet** instead of Control). Cages are built by **add-shelf / add-cage** (`d.shelves = [{no, cages:[{code}]}]`, each shelf an independent list so shelves may have **unequal** counts) with editable shelf number + cage code strings — **no fixed grid, no defaults** (blank strings). `submitBuildProject` validates blank/duplicate names + duplicate cage codes, creates **empty** cages (`groupId:null, dietId:null, mice:[]`), assembles `members`, and sets **`approval:'approved'`** — the project is live immediately, with no mice.
  - **Sci intake / first weighing** (`openIntakeCage`, gated `weigh`): mice arrive AFTER the project is live. Dashboard shows **🐭 รับหนูเข้ากรง (N กรงว่าง)** while any cage is empty; `App.intake` mode makes empty cages dashed targets (`.intake-target`) and dims filled ones. Per cage: pick the **sex (one per cage)**, then "ชั่ง & เพิ่มหนู" opens the **two-card pad** — ลำดับในกรง (1…`MAX_CAGE_NO`) + **น้ำหนักที่ชั่งได้** (decimal; the pad grows a `.` key only while the weight card is active, bottom row is a flex `.kp-row`). Saving mints the animals: `freshMouse(mouseCode(p.id, cage.code, cageNo), sex, null, cageNo, weight)` — permanent code issued here, `groupNo` null, cage still on the default diet.
  - **PI grouping** — see the จัดการกรง entry below. The two layers are assigned there, separately, at any time after intake.
- **Weights are always displayed to 1 decimal place, unit grams.** Use `App.g(v)` (plain) and `App.gs(v)` (signed). Never format grams inline.
- **Cage status colour**: gray = normal, yellow = "care" (any living mouse with `careOpen` or `humaneOrder`). Computed by `App.cageStatus(cage)`.
- **Mouse status colour** (by daily weight change, `App.mouseStatus`): green = gain ≥ `App.GAIN_THRESHOLD` (0.2 g), yellow = 0–0.2 g, red = ≤ 0 (loss/no gain). Dead or stopped mice = no status colour.
- **Group averages** (reports, control comparison) exclude mice where `!Data.inStats(m)` (dead or stopped).
- **Weighing mode** (SCI only, routine rounds — distinct from intake): entering it starts `App.weighSession` — all cages go gray and values are cleared ("not weighed yet"); each saved cage turns green. Exit restores real values/colours. The wizard weighs **alive mice only** (`w.mice = cage.mice.filter(m => m.alive)`); dead mice are skipped. The button only appears once the project has mice; while it is empty the **intake** button takes its place.
- **จัดการกรง** (dashboard "✏️ จัดการกรง", `App.editing`, gated by `editProject` = PI/CoPI/ADMIN, approved & not-closed): **after the project starts, cages and mice are FIXED** — this screen can no longer add or delete shelves, cages or mice (`openCageEditor` and the whole structural editor were removed). It does exactly **three jobs, one at a time**, chosen with `App.editMode`:
  1. **🍚 กำหนดชนิดอาหาร** — pick a diet chip (arms `App.dietBrush`), then tap cages.
  2. **💊 กำหนดสารทดสอบ** — pick a group chip (`App.groupBrush`, plus a **✕ เอาออกจากกลุ่ม** chip), then tap cages.
  3. **↔️ ย้ายกรงไปชั้นอื่น** — tap a cage (`App.moveCageId`), then **⬇️ ย้ายมาชั้นนี้** in the target shelf header. The cage keeps its code, mice and both group layers; only `shelf`/`position`/`shelfLabel` change and the old shelf re-packs to 1..N.
  Switching sub-mode clears the armed brush/selection so the two assignment jobs never blend. Chips show live capacity (`4/6`). `applyCageEdit` routes the tap; `assignCageDiet` / `assignCageGroup` do the work and **enforce both layers' `capacity`**. Assigning a group also hands every mouse in the cage its `groupNo` (next free number in that group, project-wide) — and removing/changing a group **releases those numbers first**, so the tag renumbers correctly. All edits are logged via `App.log`.
- **Changing an assignment needs a typed confirmation**: the FIRST time a cage gets a diet or a group it applies immediately; **changing an existing one** opens `confirmDialog({ requireText: App.CONFIRM_PHRASE })` — the OK button stays disabled until the user types **`confirm change`**. The dialog states the before → after and, for สารทดสอบ, which `groupNo`s will be released. `confirmDialog`'s `requireText` option is generic — reuse it for any other "rewrite a decision already made" action.
- **Vet actions**: treatment/close-case/humane-endpoint are only reachable by clicking into an individual **mouse** (not from the cage popup). The per-mouse "⋯" kebab in the cage popup holds, gated by capability: **⚠️ แจ้งผิดปกติ** (`flag`, everyone), **Stop** (`stop`, PI-only), **แจ้งหนูตาย** (`reportDeath`), **❄️ จัดการซาก** (`handleCarcass`, while frozen).
- **Abnormal flag** (`openFlagForm`, `flag` cap = any member): reports a mouse as "looks abnormal" (not a diagnosis) with a free-text note → sets `mouse.flagOpen`/`mouse.flag = {by,note,date}`, shows an **orange "!"** on the mouse (`App.flagMark`) and turns the cage **orange** (`cageStatus` → `'flag'`, priority below care/danger). Awaits VET: from the mouse detail a VET (`treat`) resolves it via **เปิดเคส (openTreatForm)** / **Humane endpoint (openHumaneForm)** / **✓ ปกติ (clear flag)** — and opening a case, issuing a humane order, or recording death auto-clears the flag.
- **Official lab forms** (ศูนย์สัตว์ทดลอง มช.). PDF originals live in `แบบฟอร์ม/`. **Form option terms that are English on the paper form stay English verbatim — never translate them to Thai** (they are technical terms); Thai is only used for UI chrome (field labels, buttons). Data-entry forms are gated by the `treat` capability (VET):
  - **Sick Case Report** (LA Guide-AF 11.1-02) — the "รายงานอาการป่วย" form (`openTreatForm`). Structured: grouped clinical-sign checkboxes (`App.SICK_SIGNS`), supportive-action checkboxes (`App.SICK_SUPPORT`), diagnosis, treatment, recommendation (`App.SICK_RECO`). Saving pushes a treatment entry and opens the case (`careOpen`). Rendered in mouse detail as sign/support chips + recommendation.
  - **Necropsy Record** (LA Guide-AF 11.3-01) — `openNecropsyForm`, gated by `handleCarcass` (the gross exam follows whoever recorded the death; the vet later adds the AV Comment), shown only for dead mice whose `death.disposition==='necropsy'`. Per-organ exam by system (`App.NECROPSY_SYS`), each organ = N (Normal) / A (Autolysis) / X (Abnormal, note) + overall abnormal finding + AV comment → saved to `mouse.necropsy`. Read-only view via `App.renderNecropsy`.
  - **Death recording** is the two-stage flow above: `openDeathForm` (`reportDeath`) captures Date/Time/Reporter + type + note and freezes the carcass; `openCarcassForm` (`handleCarcass`, SCI/VET) then picks dispose/necropsy — choosing necropsy opens `openNecropsyForm` immediately.
  - **Monitoring Record** (LA Guide-AF 11.1-03) — the day-by-day follow-up ("การรักษา/ติดตามอาการ") derived from `mouse.treatments`.
- **Summary reports** (project-level modals, opened from the dashboard mode-bar, visible to all who can view):
  - **รายงานการตายของสัตว์ทดลอง** (`openDeathReport`) — table of every dead mouse (date, time, cage, ID, group, reporter, type, disposition, necropsy status); rows link to the mouse detail.
  - **บันทึกติดตามอาการสัตว์ป่วย** (`openSickReport`) — per treated animal, the day-by-day treatment timeline (oldest→newest) with a status badge (กำลังรักษา / หายดี / ตายแล้ว); card header links to the mouse detail.
- **Export to PDF** — every form/report has a `🖨️ Export PDF` button. No library: `App.printDocument(filename, bodyHtml)` writes a self-contained A4 HTML doc into a hidden iframe (embedded font, `App.PRINT_CSS`) and calls `print()` → user picks "Save as PDF". Doc builders return body HTML (unit-testable in isolation) and **each replicates its CMU paper form** via `cmuHeader` (2-row header band) + bordered `table.form` (`table-layout:fixed` + `COLS4`/`COLS2` colgroups so long checkbox rows wrap within the page):
  - `buildSickCaseDoc` (11.1-02), `buildMonitoringForm` (11.1-03, Day 1–14 daily grid), `buildNecropsyDoc` (11.3-01, 4 ID columns), `buildDeathReportDoc` (11.1-01, Protocol/Action-Plan + No./Date/Time/Cage/ID/Reporter table). `buildSickReportDoc` = one `buildMonitoringForm` per sick animal (page-break between).
  - Per-mouse export buttons (`ฟอร์มป่วย` / `ฟอร์มติดตาม` / `ฟอร์มชันสูตร`) live in the mouse-detail footer; the two project-level exports live in the report modals.
- **Project documents** (`openDocuments`, "📎 เอกสาร" in the dashboard mode-bar): attach important PDFs per project (`project.documents[] = { id, name, size, category, uploadedBy, date, url }`, categories in `App.DOC_CATEGORIES`). View/open is for anyone with access; attach/delete needs `editProject`. **Prototype only** — files live in memory as object URLs (`URL.createObjectURL`), lost on refresh; seed rows have `url:null` (metadata "ตัวอย่าง"). A real backend would upload to object storage + keep signed URLs.
- **Audit log**: `DB.auditLog` is append-only (header "📋 Audit Log"), filtered to projects the user can access (admin sees all). Record every meaningful action with `App.log(action, detail, projectName)`.
- **Top bar** is production-styled: brand + crumbs + Audit Log + (admin) จัดการผู้ใช้ + a **user menu** at top-right (avatar/name → dropdown with "ดูข้อมูลผู้ใช้ & สิทธิ์" and "ออกจากระบบ"). There is no standalone "สิทธิ์" tab.
- **User info & permission page** (`renderRoles`, reached via the user menu → "ดูข้อมูลผู้ใช้") is a read-only reference: capability matrix + the current user's role per project. Member/role assignment is done in-project via `openMembers(p)` (PI/admin only); admins are excluded from the "add member" list (they're superusers). The roles page also has a self-service "🔒 เปลี่ยนรหัสผ่าน" (`openMyPassword`).
- **User management** (`renderUsers`, header "👤 ผู้ใช้", gated by `manageUsers` → ADMIN + AV): CRUD system accounts (`DB.users`, fields firstName/lastName/email/password/**position**; `name` is derived and kept in sync via `makeUser`/on save). The position picker is a **single-select** `.pos-grid` (one position per account); only a full ADMIN may hand out `ADMIN`. Rules enforced: ≥1 admin always (`adminCount`/`isLastAdmin`), an admin can't demote or delete themselves, emails unique, password ≥6 chars. This screen is how an outside researcher gets an **External** account before they can log in and request a project. `App.log` records add/edit/delete/password actions.
- **Create Project** (`renderCreateProject`) is the PI **request** form only — it declares totals and proposes both group layers; no cages or mice are created here (AV builds the cages, Sci brings the mice in). `App.freshMouse(code, sex, groupNo, cageNo, weight)` is the single constructor for a live animal.

## Conventions
- Vanilla JS only, no dependencies. Keep the string-template + delegated-handler style already in `app.js`.
- Match existing Thai microcopy and the compact card/modal styling.
- When adding a mouse field, initialise it in `makeMouse` (data.js) so all generated + seeded mice have it.

## Cross-component invariants — keep these in sync when editing
These pieces are coupled; changing one without the others silently breaks behaviour:
- **Asset cache-bust**: after editing any `js/` or `css/` file, bump `?v=N` in **all four** tags of `index.html` (fonts.css, styles.css, data.js, app.js) — the preview/Pages serve the query-stringed URLs, so a stale `v` shows old code.
- **Font is embedded, not linked**: `css/fonts.css` holds IBM Plex Sans Thai (loopless) as base64 `@font-face` blobs — **never** add a Google Fonts `<link>` back. The family ships **400/500/600/700 only**, so styles.css must not request 800/900 (the browser would fake a synthetic bold). The PDF/print iframe is a separate document and needs the font too: `printDocument` resolves `css/fonts.css` via `new URL('css/fonts.css', document.baseURI)` — keep that when touching the print path, and keep `PRINT_CSS`'s `font-family` in sync with `styles.css`.
- **Capabilities**: never check a role key directly — gate via `App.can(cap, project)`. A new capability must be added to **`POSITIONS[*].caps`** and/or **`ROLES[*].caps`** *and* to **`CAPABILITIES`** (data.js), or it will silently never be granted and won't appear in the two permission matrices on the roles page.
- **Adding/renaming a POSITION**: update `POSITIONS` **and** `POSITION_ORDER` (drives the roles-page matrix, its legend, and the admin user-editor `.pos-grid`), then add a demo persona in `USERS`. Print positions via `App.positionKey()` / `positionLabel()`; `user.position` is a single string (helpers like `positionKeys()` wrap it in a one-element array for uniform `.map/.join`).
- **Demo personas must not leak position caps**: `u_pi`/`u_copi`/`u_ahs` deliberately hold only `EXTERNAL` so switching to them shows the *project role's* caps and nothing else. Give them `SCI` and they silently gain `weigh`, which hides the rule that a PI cannot weigh. `u_pisci` (position `SCI` + `projectRole PI`) demos the one legitimate "two roles" case — an internal scientist who is also PI of a project.
- **Position scope vs approval rights are different things**: `seesAllProjects` (`scope==='all'`) decides what the project list shows; `canReview` (`approve` cap) decides who gets review buttons. Don't reuse one for the other — IACUC/QA/EX see everything but approve nothing.
- **Project-role personas**: `user.projectRole` (data.js) drives the `App.myProjectRoles` override — a persona holds that role in every project. New users created in the admin editor have `projectRole: null` (correct — they're real, membership-based).
- **Top-level tabs** (`App.TABS`: โครงการ / งานคลัง / การเงิน): each tab is gated by a capability (`view` / `viewSupply` / `viewFinance`) and rendered by `visibleTabs()` in `shell()`. The bar is **hidden when only one tab is visible**, so most positions see no tabs at all. `tabOfRoute(name)` maps a route to its tab for highlighting — **add new routes there** or they will un-highlight the bar. `homeRoute()` is the landing target after login and every "not permitted" bounce; never hard-code `go('projects')` for that, since **GM has no โครงการ tab** and must land on `supply`.
- **`hasAccess` requires the `view` cap first**, then scope/membership. That is the single thing keeping GM (งานคลัง/การเงิน only) out of every project despite `scope:'all'` — don't "optimise" the `view` check away.
- **Next-phase modules**: `App.MODULES` + `renderModulePlaceholder` back the `supply` / `finance` routes (blank by design, facility-wide — **not** per project). Adding another module means keeping four things in sync: `MODULES`, a `case` in `handleNav`, a line in `go()`, and an entry in `TABS` (+ its capability in `CAPABILITIES`/`POSITIONS`).
- **Only `approved` projects are enterable**: `requested`/`aec_ok`/`rejected` projects don't open the dashboard (`renderDashboard` bounces them). Card clicks route via **`App.openProject(p)`** by stage: `requested` → creator `editProject` (request form), AEC `openProjectInfo`; `aec_ok` → AV `buildProject`, others `openProjectInfo`; `rejected` → creator `editProject`, others read-only. `editProject` loads the **request** into `this.draft` (mode `request`, `editId`); `submitCreateProject` resubmits it. The "+ สร้างโครงการ" button clears `this.draft` first so a stale edit/build draft never leaks into a new request.
- **Visibility & roles across stages**: `App.isReal(p)` (= `approved`) is the line between "pipeline paperwork" and "physically exists" — `hasAccess` and `myProjectRoles` use it, so an approved-but-empty project is already visible to its whole team. Pre-`approved` stays visible only to the **creator + reviewers** (`canReview`).
- **A live project may legitimately be empty or partly ungrouped.** Anything reading a cage's group must tolerate `groupId === null` (`openCagePopup` guards `group` in all three spots; `cageCard` prints "ยังไม่จัดกลุ่ม"), and anything reading its diet must go through `cageDiet()` so the default applies. `stageInfo` shows a **🐭 รอนำหนูเข้ากรง** pill while `isEmptyProject(p)`.
- **Operational gate**: for *approved* projects, every *recording* action (weigh, flag, stop, treat/close-case, humane order, death, necropsy) is gated by **`App.isOperational(p)`** (approved & not `closed`) — so a **closed** (approved) project is view-only. `renderDashboard` (canWeigh), `openCagePopup` (kebab `operational`), and `openMouseDetail` (`canTreat`/`canNecropsy` ANDed with operational) rely on it — add new recording actions the same way.
- **Project state**: `approval` (`requested|aec_ok|approved|rejected`) is separate from operational `status` (`active|closed`). The card badge/strip, `openProject` routing, `renderDashboard` guard, `isOperational`, and `openProjectInfo` all branch on these via `approvalStage`/`stageInfo` — keep them consistent. New requests: `approval:'requested'`, `status:'active'`. Demo seed: **P1** running (both layers assigned, 4 shelves × 6 cages × 2 mice), **P3** closed, **P5** requested, **P7** aec_ok, **P6** rejected, **P8** approved-but-empty (walk the intake → grouping flow here).
- **Both group layers are edited in three places — keep them in step**: the PI request form (`renderReqGroups` + the diets equivalent), the AV build form (`renderBuildDiets`/`renderBuildGroups`), and จัดการกรง (`editModePanel` chips). Adding a field to a layer means touching all three plus `submitBuildProject`'s mapping.
- **Reports are 2-factor**: `reportState` carries **both** `dietIds` and `groupIds`, and every cage selection goes through **`App.reportCages(p[, groupId])`** — a cage is in scope only when both layers pass. Never filter cages inline in `drawReport`/`exportCSV` again, or the diet filter silently stops applying to that series. The CSV exports `Cage · Diet · Group · NoInGroup · Tag` so the sheet pivots either way.
- **Abnormal flag lifecycle**: `openFlagForm` sets `flagOpen`/`flag`; it is cleared in the saves of `openTreatForm`, `openHumaneForm`, `openDeathForm`, and the mouse-detail "✓ ปกติ" handler. Any new resolution path must clear it. Shown by `App.flagMark` + `cageStatus`→`'flag'` + `.m-badge.flag`.
- **Cage status priority**: `cageStatus` returns danger > care > flag > normal; each needs a matching `.cage.<s>` + `.dot.<s>` CSS rule and a dashboard-legend entry.
- **Project documents** are reachable **only** via `openProjectInfo` → `📎 จัดการเอกสาร` (gated `editProject`). AV approval reviews these files, so never remove that path without providing another.
- **Card click vs buttons**: the project card is opened by a click handler on `.card-open` that ignores `.card-menu`/`[data-act]` targets; every interactive control inside a card calls `e.stopPropagation()`. Add new in-card controls the same way or they'll trigger navigation.

## Out of scope for this prototype (per spec)
KPI dashboard, notifications, audit log, fine-grained permissions, real import/export (Excel export is a client-side CSV), mobile version, DB optimization. Don't build these unless asked.
