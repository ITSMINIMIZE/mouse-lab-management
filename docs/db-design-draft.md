# โครงข้อมูล Firestore — ดราฟต์

> **สถานะ: ดราฟต์ ยังไม่ลงมือ** — เก็บไว้รอเคลียร์หน้าเว็บให้เรียบร้อยก่อน
> ปรับปรุงล่าสุด 6 ก.ย. 2569

## สิ่งที่ตกลงกันแล้ว

| เรื่อง | ที่เลือก | ผลต่อโครงสร้าง |
|---|---|---|
| โปรเจกต์ | `ilamp-bb0f1` · Firestore สร้างแล้ว (production rules) · Auth เปิดแล้ว | — |
| Region | `asia-southeast1` (สิงคโปร์) | **เปลี่ยนไม่ได้** ย้ายต้องสร้างโปรเจกต์ใหม่ |
| ขอบเขต | หน่วยงานเดียว · ที่อื่นจะทำแยกชุด | คอลเลกชันอยู่ระดับบนสุดได้เลย ไม่ต้องมีชั้น facility |
| Export Excel | ทำในเบราว์เซอร์ | ทุกแถวต้อง**อ่านออกได้ด้วยตัวเอง** ไม่ต้องไป join |
| ออฟไลน์ | **สำคัญมาก** | ID สร้างฝั่งเครื่อง · ความไม่ซ้ำต้องพึ่ง document ID |

## หลักที่ยึด 4 ข้อ

1. **ประวัติแยกเป็นคอลเลกชันระดับบนสุด ไม่ฝังในเอกสารแม่**
   เอกสารจำกัด 1 MiB — หนู 48 ตัว × ชั่งรายสัปดาห์ × หลายเดือน ฝังไม่รอด และฝังแล้ว export เป็นแถวไม่ได้

2. **ทุกแถวประวัติพกชื่อที่อ่านออกติดตัว ไม่ใช่แค่ id**
   Firestore ไม่มี join + export ทำในเบราว์เซอร์ + ต้องทำงานออฟไลน์ = ไล่ถามข้ามคอลเลกชันไม่ได้
   เก็บ `projectName` `mouseCode` `cageCode` `groupName` ลงในแถวเลย
   วิธีเดียวกับที่แช่แข็งราคาหัตถการไว้แล้ว และถูกต้องด้วย เพราะประวัติควรบันทึกสิ่งที่จริง ณ ตอนนั้น

3. **อะไรที่ห้ามซ้ำ → ใช้เป็น document ID**
   ออฟไลน์เช็กซ้ำกับเซิร์ฟเวอร์ไม่ได้ แต่ document ID ซ้ำไม่ได้โดยตัวฐานข้อมูลเอง
   → เลข SOP · รหัสหัตถการ · เลขครุภัณฑ์

4. **ID สร้างจากฝั่งเครื่องเสมอ** ไม่มีเลขรันจากเซิร์ฟเวอร์ ไม่งั้นบันทึกตอนเน็ตหลุดไม่ได้

## โครงคอลเลกชัน

```
config/rates                    อัตราค่าฝากเลี้ยง · ระยะกักโรค · รายการหัตถการ
users/{uid}                     uid จาก Firebase Auth · ไม่เก็บรหัสผ่าน
sops/{เลข SOP}                  ID = เลขเอกสาร
assets/{เลขครุภัณฑ์}             + ยอดสะสมการใช้งาน (ครั้ง/นาที) ไว้ในเอกสาร

projects/{projectId}            หัวโครงการ · request (หลักฐาน แช่แข็ง) · facility · diets · groups · members
  └ cages/{cageId}
  └ mice/{mouseId}              ไม่ซ้อนใต้กรง — เก็บ cageId เป็นฟิลด์

weights/{id}                    ชั่งน้ำหนัก
healthEvents/{id}               แจ้งผิดปกติ · รักษา · humane · ตาย · ชันสูตร
doses/{id}                      ให้สารทดสอบ
careRounds/{id}                 ตรวจดูแลกรง
quarantineDaily/{id}            ดูแลประจำวันช่วงกักโรค
assetUsage/{id}                 การเรียกใช้ครุภัณฑ์
assetMoves/{id}                 รับเข้า/เบิกออกวัสดุ
assetRepairs/{id}               แจ้งซ่อม
expenses/{id}                   ค่าน้ำ ไฟ ค่าจ้าง
auditLog/{id}
```

ทุกคอลเลกชันกลุ่มล่างมี `projectId` + `date` + ชื่อที่อ่านออก
→ หนึ่ง query ได้แถวพร้อม export และหน้าการเงินใช้ index เดียวกันได้

## ต่างจากของเดิมตรงไหน

| ตอนนี้ (in-memory) | จะเป็น | เหตุผล |
|---|---|---|
| หนูซ้อนอยู่ในกรง | หนูอยู่ระดับโครงการ มี `cageId` | อ่านทั้งโครงการง่าย · ย้ายกรงแก้ฟิลด์เดียว |
| น้ำหนัก/สุขภาพ ฝังในตัวหนู | คอลเลกชันแยก | ชนเพดาน 1 MiB + export ไม่ได้ |
| `PROCEDURES` เป็นค่าคงที่ในโค้ด | `config/rates` | หน้าอัตราค่าบริการแก้ได้อยู่แล้ว |
| ตำแหน่ง/สิทธิ์ 27 ข้อ | **อยู่ในโค้ดเหมือนเดิม** | ไม่ใช่ข้อมูลที่ผู้ใช้แก้ · ทำให้ Security Rules ง่ายกว่ามาก |

## รายการหัตถการและหน่วย (ได้จากเจ้าของงาน 6 ก.ย. 2569)

โครงสร้างหนึ่งรายการ = **ชื่อ · ราคา · หน่วย** — ทำในแอปแล้ว (`PROC_UNITS` / `PROCEDURES` ใน `js/data.js`)

หน่วยที่รองรับ 10 หน่วย และช่องที่ต้องกรอกของแต่ละหน่วย:

| หน่วย | ต้องกรอก | ปริมาณที่คิดเงิน |
|---|---|---|
| บาท / ตัว | หนู | ตัว |
| บาท / ครั้ง | จำนวนครั้ง | ครั้ง |
| บาท / ตัว / วัน | หนู × วัน | ตัว-วัน |
| บาท / ตัว / ครั้ง | หนู × ครั้ง | ตัว-ครั้ง |
| บาท / มิลลิลิตร / ตัว | มล. × หนู | มล.-ตัว |
| บาท / ชั่วโมง | ชั่วโมง | ชั่วโมง |
| บาท / กล่อง | กล่อง | กล่อง |
| บาท / กิโลเมตร | ระยะทาง | กม. |
| บาท / โครงการ | — | 1 โครงการ |
| บาท / กิโลกรัม | น้ำหนัก | กก. |

**ค่าใช้จ่ายเกิดได้ 2 ทาง** ทั้งสองทางใช้อัตราชุดเดียวกันและสูตรเดียวกัน:

| ทาง | เก็บที่ | ความหมาย |
|---|---|---|
| 1. PI ร้องขอตั้งแต่แรก | `projects/{id}.request.services[]` | **ประมาณการ** ในคำขอ · แช่แข็งราคา ณ วันยื่น · ยังไม่เรียกเก็บ |
| 2. เกิดขึ้นภายหลัง | `projects/{id}.billing.services[]` | **ยอดเรียกเก็บจริง** รายเดือน · มีธง `src` ว่าตรงกับที่ขอไว้หรือเป็นของใหม่ |

หน้าการเงินจึงเทียบ "ขอไว้ / ทำจริง" ได้ (`src: 'quoted' | 'extra'`)

### ⚠️ ประเด็นที่ต้องตัดสินตอนลง DB

- `billing.services[]` เป็น array ในเอกสารโครงการ — โครงการยาว ๆ จะโตชนเพดาน 1 MiB
  ควรแยกเป็นคอลเลกชัน `serviceCharges/{id}` เหมือนคอลเลกชันกลุ่มล่างอื่น ๆ (มี `projectId` + `date`)
  ส่วน `request.services[]` เก็บใน `request` ต่อไปได้ เพราะเป็นหลักฐานที่แช่แข็งแล้ว ไม่โตอีก
- แถวที่บันทึกแล้วเก็บทั้ง `unit` และตัวเลขที่กรอก (`mice` `days` `ml` …) ติดไปด้วย
  เพื่อให้อ่านย้อนได้ว่ายอดมาจากการคูณอะไร แม้อัตรากลางจะถูกแก้ไปแล้ว
- เพิ่มหน่วยใหม่ในอนาคต = แก้ `config/rates.units` ไม่ต้องแก้โค้ด (ตอนนี้ยังอยู่ในโค้ด)

## เลขที่เอกสาร SOP (ได้จากเจ้าของงาน 6 ก.ย. 2569)

```
รหัสหน่วยงาน - รหัสส่วนงาน - รหัสหมวดงาน - ลำดับ/ลำดับย่อย
MEDCMU       - LAU        - LAA         - 001/1
MEDCMU       - IACUC      -             - 001      ← หมวดงานว่างได้
```

- **หน่วยงาน** `MEDCMU` — หน่วยสัตว์ทดลอง คณะแพทยศาสตร์ มหาวิทยาลัยเชียงใหม่
- **ส่วนงาน** `LAU` (มีหมวดย่อย `LAA` `LAC` `LAF` `LAE`) · `IACUC` · `ENG` · `OHS`
- **หมวดงาน** ว่างได้ — ความลึกจึงไม่คงที่

### ⚠️ `/` ใช้เป็น document ID ไม่ได้

`/` เป็นตัวคั่น path ของ Firestore — `.../001/2` จะกลายเป็นคนละ path
แต่เราต้องการให้ ID เป็นเลขเอกสาร เพื่อให้**ความไม่ซ้ำมาฟรี** (ออฟไลน์เช็กกับเซิร์ฟเวอร์ไม่ได้)

**ทางแก้: แตกเป็นฟิลด์ แล้วประกอบตอนแสดงผล**

```
sops/{MEDCMU-LAU-LAA-001_2}        ← ID: แทน / ด้วย _
  org:      "MEDCMU"
  section:  "LAU"
  category: "LAA"                  ← ว่างได้
  seq:      1
  sub:      2                      ← ว่างได้
  no:       "MEDCMU-LAU-LAA-001/2" ← ข้อความที่คนอ่าน สร้างจากฟิลด์ด้านบน
```

ได้เพิ่มอีก 3 อย่างที่เก็บเป็นข้อความก้อนเดียวทำไม่ได้:
- กรองตามส่วนงาน/หมวดงานได้
- เรียงลำดับถูกต้อง (เรียงข้อความจะได้ `001/10` มาก่อน `001/2`)
- ออกเลขถัดไปให้อัตโนมัติตอนเพิ่มฉบับใหม่

### ลำดับย่อย = หัวข้อย่อย (ยืนยันแล้ว 6 ก.ย. 2569)

`001/1` `001/2` คือ **หัวข้อย่อยภายใต้หัวข้อเดียวกัน** ไม่ใช่ฉบับแก้ไข
→ `seq` + `sub` เก็บโครงสร้างหัวข้อ ส่วน `version` เก็บฉบับแก้ไข **เป็นคนละเรื่อง อยู่คนละฟิลด์**

ผลที่ตามมาต่อหน้าจอ:
- SOP ที่ `seq` เดียวกันคือกลุ่มเดียวกัน — แผง SOP ควรแสดงเรียงติดกันและเห็นว่าเป็นพวกเดียวกัน
- เรียงต้องใช้ `seq` แล้วตามด้วย `sub` เป็นตัวเลข ไม่ใช่เรียงข้อความ
- ตอนเพิ่มฉบับใหม่ ระบบเสนอได้ทั้ง "หัวข้อถัดไป" (`seq`+1) และ "หัวข้อย่อยถัดไป" (`sub`+1)

## ยังไม่ตัดสินใจ

- **ไลบรารีสร้างไฟล์ Excel** — SheetJS (.xlsx จริง หลายชีต จัดรูปแบบได้ ~1 MB ต้องเก็บไว้ในโปรเจกต์เพื่อให้ออฟไลน์ทำงาน) vs CSV (ไม่ต้องพึ่งอะไร แต่ชีตเดียว ไม่มีรูปแบบ และภาษาไทยต้องใส่ BOM)
  ผมเอนไปทาง SheetJS เพราะโจทย์คือ "ทุกรายการต้อง export Excel ได้" ซึ่งฟังดูเป็นเอกสารที่เอาไปใช้ต่อจริง

## ยังไม่ได้เขียนในดราฟต์นี้

- รายละเอียดฟิลด์ทุกคอลเลกชัน
- Security Rules (แปลตารางสิทธิ์ 27 ข้อเป็น rules)
- แผนย้ายข้อมูลจาก `js/data.js` เป็น seed script
- การแยก `js/data.js` เป็นนิยามระบบ / ข้อมูลตัวอย่าง เพื่อให้ลบออกตอนส่งมอบได้
