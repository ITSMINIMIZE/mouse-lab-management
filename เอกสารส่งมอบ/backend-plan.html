01 สถาปัตยกรรมที่เลือก

ตัดสินใจแล้ว: Firebase — Hosting เสิร์ฟหน้าเว็บ, Firestore เป็นฐานข้อมูล, Firebase Auth ทำระบบล็อกอิน ตัวแอปเป็น static ล้วนไม่มี build step อยู่แล้ว จึง deploy ได้ตรง ๆ · ทางเลือก on-prem เก็บไว้เป็นแผนสำรองกรณีนโยบายข้อมูลไม่อนุญาตให้ใช้คลาวด์

02 โครงข้อมูลบน Firestore

Firestore เป็น document store ไม่มี join และไม่มี aggregate ข้ามคอลเลกชัน — แต่ขนาดงานจริงของหน่วยนี้เล็ก (โครงการละไม่กี่สิบตัว) การดึงหนูทั้งโครงการมาคำนวณค่าเฉลี่ยกลุ่มฝั่ง client จึงทำได้สบาย ซึ่งเป็นสิ่งที่ js/app.js ทำอยู่แล้ววันนี้ ข้อควรระวังจริง ๆ อยู่ที่รูปทรงของข้อมูล ไม่ใช่ความสามารถในการคำนวณ

● กติกาที่ต้องยึด

  • ห้ามยัดทุกอย่างไว้ในเอกสารเดียว — เอกสาร Firestore จำกัด 1 MiB โครงการที่มีหนู 48 ตัว × น้ำหนักรายวัน × ประวัติสุขภาพ จะชนเพดานแน่นอน
  • แตกเป็น subcollection ตามชั้นข้อมูลจริง
  • Firestore คิดเงินรายเอกสารที่อ่าน — หน้าที่เปิดบ่อยควรอ่านเฉพาะที่ใช้ และเก็บยอดสรุปไว้ในเอกสารแม่
  • เปิด offline persistence — ห้องเลี้ยงสัตว์สัญญาณไม่ดี ข้อนี้ได้เปรียบ Postgres ชัดเจน

● สิ่งที่ได้มาฟรี

  • Realtime — คนหนึ่งบันทึกน้ำหนัก อีกจอเห็นทันที ไม่ต้องเขียน websocket เอง
  • Auth ครบชุด — ล็อกอิน · รีเซ็ตรหัสผ่านทางอีเมล · MFA
  • ไม่ต้องดูแลเซิร์ฟเวอร์ ไม่ต้อง backup เอง
  • ค่าใช้จ่ายที่ขนาดงานนี้น่าจะอยู่ในโควตาฟรีหรือใกล้เคียง
// โครงคอลเลกชันที่เสนอ — แตกตามชั้นที่ข้อมูลโตจริง projects/{projectId} // หัวโครงการ · request · phase · billing · quarantine cages/{cageId} // รหัสกรง · ชั้น/แร็ค · diet · group mice/{mouseId} // รหัสหนู · เพศ · สถานะ · ผลสรุปล่าสุด weights/{weightId} // โตทุกวัน — ต้องแยกออกมา health/{entryId} // ไทม์ไลน์สุขภาพ · การรักษา careLog/{roundId} // รอบตรวจกรงของ ACT quarantineDaily/{dayId} // บันทึกดูแลระหว่างกักโรค assets/{assetId} // พัสดุ — วัสดุ + ครุภัณฑ์ moves/{moveId} // รับเข้า/เบิกออก repairs/{repairId} finance/rates // อัตรากลาง + รายการหัตถการ finance/expenses/{expenseId} // ค่าน้ำ ไฟ ค่าจ้าง users/{uid} // ตำแหน่ง · ข้อมูลติดต่อ (Auth เก็บรหัสผ่านเอง) auditLog/{entryId}

03 ล็อกอิน สิทธิ์ และ 2FA

วันนี้หน้าล็อกอินยังไม่ตรวจรหัสผ่านเลย — พิมพ์อะไรก็เข้าได้ ขอแค่อีเมลตรงกับบัญชีที่มี เพราะเป็นโปรโตไทป์คลิกผ่าน รหัสผ่านที่เก็บอยู่จึงเป็นแค่ข้อมูล ยังไม่ใช่ด่าน · Firebase Auth ทำให้เป็นด่านจริงและแถมสองอย่างที่ค้างอยู่มาพร้อมกัน

● ได้มาทันทีจาก Firebase Auth

  • ลืมรหัสผ่าน — ส่งลิงก์รีเซ็ตทางอีเมล ผู้ใช้ตั้งใหม่เอง ไม่ต้องรบกวนผู้ดูแลระบบ
  • รหัสผ่านถูกแฮชและเก็บฝั่ง Google — ระบบเราไม่เห็นและไม่ต้องเก็บเอง
  • ปิดกั้นการเดารหัสซ้ำ ๆ ให้ในตัว
  • รหัสผ่านเริ่มต้นที่ผู้วิจัยตั้งมาในคำขอ ใช้เป็นรหัสแรกเข้าแล้วบังคับเปลี่ยนได้

● 2FA — เลือก TOTP

  • TOTP (Google / Microsoft Authenticator) — ไม่มีค่าใช้จ่ายต่อครั้ง สแกน QR ครั้งเดียวจบ
  • ไม่เลือก SMS เพราะมีค่าต่อข้อความและต้องผูกกับผู้ให้บริการภายนอก
  • ต้องทำ: เก็บ secret ต่อผู้ใช้ · หน้าเปิดใช้งาน (QR) · ขั้นกรอก 6 หลัก · รหัสสำรองเผื่อทำมือถือหาย
  • ทำพร้อมกับตอนต่อ Auth ไม่ใช่แปะทีหลัง
⚠

ตรวจราคาก่อนสัญญากับลูกค้า — MFA บน Firebase Auth ต้องใช้แพลนแบบเสียเงิน (Blaze) และ TOTP ต้องอัปเป็น Firebase Authentication with Identity Platform ซึ่งคิดตามจำนวนผู้ใช้ต่อเดือน จำนวนผู้ใช้ของหน่วยนี้น้อยมากจึงน่าจะอยู่ในโควตาฟรี แต่ราคาปัจจุบันต้องเช็กจากหน้าเว็บ Google เอง ตัวเลขในเอกสารนี้ไม่ได้ระบุไว้เพราะเปลี่ยนได้

➡

สิทธิ์ต้องย้ายไปฝั่งเซิร์ฟเวอร์ — ตอนนี้ตารางสิทธิ์ (26 ความสามารถ · ตำแหน่งระดับระบบ ∪ บทบาทในโครงการ) เช็กอยู่ใน js/app.js ล้วน ซึ่งเปิด DevTools ก็ข้ามได้ ในระบบจริงต้องเขียนซ้ำเป็น Security Rules โดยเก็บตำแหน่งไว้ใน custom claims ของ Auth และเก็บบทบาทรายโครงการไว้ใน projects/{id}/members ให้ rules อ่าน — โค้ดหน้าบ้านยังเช็กต่อไปได้เพื่อซ่อนปุ่ม แต่ตัวบังคับจริงต้องอยู่ที่ rules

04 การแนบเอกสาร PDF

แต่ละโครงการแนบเอกสารสำคัญได้ (โปรโตคอล · ใบอนุมัติ EC · SOP · ผลแล็บ) — เดโมหน้าตาพร้อมแล้วในตัว prototype ส่วนของจริงใช้แนวทางมาตรฐานคือแยกไฟล์ออกจากฐานข้อมูล

● ในเดโมตอนนี้ (ทำแล้ว)

  • ปุ่ม เอกสาร ในหน้าโครงการ — แนบ / เปิด / ลบ PDF
  • เก็บไฟล์เป็น object URL ในหน่วยความจำ
  • คุมสิทธิ์: ดูได้ทุกคนที่เข้าถึง · แนบ/ลบเฉพาะ PI
  • ข้อจำกัด: รีเฟรชแล้วหาย — ไว้โชว์ UX เท่านั้น

● ในระบบจริง

  • ตัวไฟล์ → object storage (ไม่เก็บ BLOB ในฐานข้อมูล)
  • metadata → ตาราง documents
  • เปิดผ่าน signed URL (หมดอายุได้) คุมสิทธิ์รายโครงการ
  • แนบได้ทั้งระดับโครงการและระดับเคส (สแกนใบชันสูตร ฯลฯ)
// metadata ของไฟล์ (ตัวไฟล์อยู่บน Cloud Storage) projects/{projectId}/documents/{docId} { filename: string, mime: string, size: number, storagePath: string, // path บน Cloud Storage category: string, // protocol · ec · sop · lab · quarantine mouseId: string | null, // null = เอกสารระดับโครงการ uploadedBy: string, uploadedAt: timestamp }
